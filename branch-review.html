01 / THE CHANGE IN ONE MINUTE

Same call. Correct default.

Previously, a caller could fill in a base method's default before runtime dispatch selected an overriding method. The override then received an already-filled argument and never got a chance to use its own default.

The branch sends undefined for omitted arguments to ordinary emitted TypeScript functions. At function entry, each parameter with an initializer is replaced only when its value is strictly undefined. Runtime dispatch has already selected the implementation by then.

02 / START HERE

A small compiler vocabulary

A compiler translates source code into a lower-level program. PXT uses TypeScript's syntax and type information, emits an intermediate representation (IR), then produces simulator JavaScript or native code. This branch changes the shared emitter, not the dispatch tables themselves.

TermMeaning here
Caller / calleeThe code making a call / the function selected to run.
InitializerThe expression after = in amount = 20. It can compute a value, not just name a constant.
Static signatureWhat the compiler knows at the call site. A variable typed as a base class can hold a derived instance.
Dynamic dispatchChoosing the actual method at runtime. A virtual call uses the class hierarchy; an interface call uses a member identity. Neither should let the caller choose an override's default.
ActionPXT's callable function value, potentially carrying captured variables, such as a callback.
PrologueSetup at the start of a function, before its user-written body.
Arity wrapperAn entry adapter for argument counts. Missing argument slots can be filled with undefined.
Shim / helperA comment-annotated API redirected to runtime/native code or a helper implementation. This branch keeps caller-side defaults for these annotated declarations.
03 / THE BEHAVIORAL DIFFERENCE

Follow one argument

The base declaration defaults to 10. The derived implementation defaults to 20. Every class/interface scenario below ultimately calls the derived implementation. The direct-call comparison uses an ordinary function with default 20.

Illustrative TypeScript, not copied from a testing file
class Base {
    value(amount = 10): number { return amount; }
}
class Derived extends Base {
    value(amount = 20): number { return amount; }
}
const receiver: Base = new Derived();
receiver.value(); // Before: 10. After: 20.

interface Reader { value(amount?: number): number; }
const reader: Reader = new Derived();
reader.value();   // Before: undefined. After: 20.
04 / ANNOTATED SOURCE

Three connected emitter changes

A. Leave the decision to emitted functions

Before / exact statement
args.push(prm.initializer)
After / exact statements
const needsCallerDefault = attrs.helper || attrs.shim;
args.push(needsCallerDefault ? prm.initializer : irToNode(emitLit(undefined)))

This helper only fills omitted trailing arguments. For ordinary functions, it emits the value undefined instead of copying the declaration's initializer into the call. An explicitly supplied argument, including explicit undefined, is not changed here.

The adjacent diagnostic 9212 now restricts nonnumeric default expressions only for shims/helpers when unfetteredInitializers is off. Ordinary emitted functions no longer hit that caller-side literal restriction. That is a language capability change as well as a dispatch fix.

The complete changed caller-side condition
After / exact excerpt, excluding source comments
const needsCallerDefault = attrs.helper || attrs.shim;
if (needsCallerDefault && !opts.unfetteredInitializers && !isNumericLiteral(prm.initializer)) {
    userError(9212, lf("only numbers, null, true and false supported as default arguments for shims and helpers"))
}
args.push(needsCallerDefault ? prm.initializer : irToNode(emitLit(undefined)))

attrs comes from parseComments(decl). irToNode lets a generated IR value travel through the expression-based argument pipeline. The existing type-check loop still checks only the originally supplied arguments, using the saved goodToGoLength.

The helper named isNumericLiteral also admits several special literals and certain property accesses that emit a numeric literal. The diagnostic's wording is not an exhaustive new grammar specification.

Source: addDefaultParametersAndTypeCheck, line 2349.

B. Guard each default in the shared function body

After / exact excerpt, emitter.ts at line 3191
if (parameter.initializer && !attrs.shim && !attrs.helper) {
    const supplied = proc.mkLabel("defaultarg");
    proc.emitJmpZ(supplied, ir.rtcall("pxt::eqq_bool", [l.load(), emitLit(undefined)]));
    proc.emitExpr(l.storeByRef(emitEscapedExpression(parameter.initializer, "initializer")));
    proc.emitLbl(supplied);
    proc.stackEmpty();
}
  1. l is a parameter slot (an IR cell). l.load() reads its incoming value.
  2. pxt::eqq_bool requests strict equality against undefined.
  3. emitJmpZ means jump if the comparison is zero/false. A supplied value skips the initializer; the label name supplied describes that destination.
  4. Otherwise, emit the initializer expression and store the result in the parameter, using the existing by-reference-aware store helper.
  5. Both paths meet at the label. stackEmpty() emits an IR stack-balance checkpoint, not a clearing of the argument value.
Readable equivalent / explanatory pseudocode, not generated output
if (amount === undefined) {
    amount = /* this implementation's initializer */ 20;
}
// The user-written function body follows.

The loop walks parameters in declaration order. The guard sits after captured-parameter storage setup and before constructor parameter-property assignments, field initializers, and the user-written body.

Source: emitFuncCore parameter setup, line 3164.

C. Destructure the resolved argument

Before / exact statement
destructuredParameters.forEach(dp => emitVariableDeclaration(dp))
After / exact statement
emitVarOrParam(parameter, l.load(), typeOf(parameter));

Previously, the generic declaration path could select the parameter's initializer as its destructuring source. Now object destructuring happens immediately after default resolution and receives the actual parameter slot explicitly. A supplied object is respected, and the outer initializer is not evaluated again just to unpack it.

Source: object parameter branch, line 3198; unchanged helper: emitVarOrParam, line 4800.

D. Update the public language contract

Removed from known semantic issues / exact text
* default parameters are resolved at call site; they should be resolved in the
        called method so eg. virtual methods can have different defaults
Added to supported features / exact text
* default parameter initializers, evaluated in the called TypeScript function
        when an argument is omitted or `undefined`, including on virtual/interface calls

This accurately describes the ordinary emitted-function path. A useful documentation clarification would be to explicitly mention shim/helper exceptions, because a simulator shim dummy can also have a TypeScript body yet deliberately skip this new prologue.

Source: language feature addition, line 41; removed limitation at the merge base, line 286.

05 / SUPPORTING SOURCE

Where the call paths converge

Putting defaults only in an argument-count wrapper would be insufficient. A call can already have enough slots and still contain undefined; optimized entries can also bypass the wrapper entirely.

Native: why wrapper skipping does not skip defaults
Unchanged backend excerpt / backbase.ts
if (this.proc.useExactIfaceWrapper) {
    this.write(`${this.proc.label()}_iface:`)
    this.write(`b ${this.proc.label()}_nochk`)
    if (!this.proc.info.usedAsValue)
        return
}

The regular wrapper compares the argument count against proc.args.length. If enough slots exist it branches to _nochk; otherwise it expands the argument area with zero-encoded undefined slots before calling that entry. The new default guard is emitted into proc.body, downstream of those entries.

The zero above is a tagged runtime representation of undefined, not JavaScript number 0. emitLit uses target-aware literal encoding. Do not read the native zero padding as a numeric default.

Sources: wrapper entries, line 1827; shared native entry, line 254; wrapper eligibility, line 1055; literal encoding, line 3887.

Simulator: strict equality and callback argument setup
Unchanged JS operator mapping / exact entry
"pxt::eqq_bool": "===",

The simulator backend uses strict equality, not loose equality or a truthiness check. It copies s.lambdaArgs[i] into parameter slots before emitting the IR body. Reading past the end of the lambda argument array yields undefined, which the new guard can resolve.

Sources: strict equality mapping, line 22; lambda setup, line 241.

IR: a parameter is not always a plain local variable

A captured, written local can use an indirect storage cell. The emitter creates that storage before the defaults loop. l.load() and l.storeByRef(...) use the existing indirection-aware operations instead of assuming a raw slot assignment. This is a sound reuse of the storage abstraction; it is not an execution check of every closure scenario.

emitEscapedExpression currently delegates directly to emitExpr. Its name does not imply extra validation, sanitization, or escape-analysis guarantees in this branch.

Sources: cell load/store helpers, line 353; emitEscapedExpression, line 1109.

06 / REVIEW BOUNDARIES

What this does not promise

Default trigger for ordinary emitted TypeScript parameters with an initializer
Incoming valueRun initializer?Reason
OmittedYes, after argument paddingThe slot contains undefined.
Explicit undefinedYesThe same strict-equality guard applies, independent of the caller's argument count.
0, false, empty stringNoFalsy is not the same as undefined.
nullNoStrict equality does not merge null with undefined.
A supplied objectNoDestructuring uses the supplied object after default resolution.

Order and side effects now belong to the callee

Illustrative initializer order / expected from the new IR sequence
let calls = 0;
function nextValue(): number {
    calls += 1;
    return calls;
}
function pair(first = nextValue(), second = first + 1): number {
    return first * 100 + second;
}
pair();             // first = 1, second = 2, result = 102
pair(8);            // first = 8, second = 9, result = 809
pair(undefined, 9); // first = 2, second = 9, result = 209

Parameters are processed left to right. A later initializer can read an earlier resolved parameter. An initializer executes only when its own slot is undefined, and ordinary callee defaults execute after the caller's argument expressions have been evaluated. These examples explain source intent; they were not compiled with PXT for this report.

Illustrative object parameter / one outer initializer, then destructuring
function read({ value }: { value: number } = { value: 3 }): number {
    return value;
}
read();             // Resolve missing object to { value: 3 }, then unpack: 3
read({ value: 9 }); // Keep supplied object, then unpack: 9

The changed condition is specifically ObjectBindingPattern. It is not a general overhaul of array destructuring, nested binding-element defaults, or all ECMAScript parameter-scope rules.

07 / DECISION

Approval guide

Support the approach based on source review. Keep execution sign-off separate.

The fix addresses the cause: default selection happened before the actual method was selected. Both halves are necessary: sending undefined without a callee guard loses defaults; adding a guard without removing caller defaults still lets the caller override the implementation's default.

No blocking source defect was identified within the inspected non-testing scope. That is narrower than saying the compiler is verified correct. The most useful nonblocking follow-up is a short documentation qualifier for shims/helpers.

Understanding checklist

These are personal understanding markers, not build or runtime verification. They are not saved or submitted.

Three quick self-checks

Would changing only the caller to pass undefined fix this?

No. Without the new function-entry guard, the implementation would receive undefined rather than evaluate its default. Caller deferral and callee resolution must ship together.

Why not check whether the number of supplied arguments is too small?

A call can explicitly pass undefined while still supplying every argument slot. Default semantics are value-based. Count padding gets the slots ready; the strict undefined check decides whether to initialize.

Does an initializer run again when an object parameter is unpacked?

Not via this changed path. The guard first resolves the slot. The object-binding helper receives l.load() explicitly, so it destructures that value instead of selecting the outer initializer again.

Suggested source-review comment

The caller/callee split makes sense: ordinary calls preserve undefined until the selected implementation resolves its defaults. The shared-body placement covers wrapper-skipping entries, and destructuring consumes the resolved parameter. Please clarify the shim/helper exception in the language documentation. My review here excludes testing files and does not independently establish runtime or performance correctness.
